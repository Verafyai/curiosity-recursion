# Curiosity Recursion v0.2: design in plain English

This note explains what v0.2 changes and why. The full specification is `docs/CR-V0.2-UPGRADE-SPEC.md`;
the hypotheses and decision rule are frozen in `bench/PREREGISTRATION-v0.2.md`. Citation keys refer to
`paper/refs.bib`. No benchmark numbers appear here: results live only in generated files.

## The problem v0.2 targets

v0.1.0 diagnostics (aggregates over all six benchmark people, `eval/corpus/diagnose.py`) showed that the
CR strategies spent a large share of their tool calls on exact repeats and on calls that returned
nothing, and that strategies used very different shares of the budget B. v0.2 is designed to spend every
call on something new, and to compare strategies at a matched number of calls as well as at B = 100.

## The parts

**1. Search ledger (the core fix).** Every tool call is first written as a query spec (tool, terms,
filters) and reduced to a canonical id: case, punctuation, accents, word order and "St." vs "Saint"
do not matter. The ledger lives in the orchestrator workflow and is shared by all workers. An exact or
near repeat (word overlap of 0.8 or more) is refused before the call, so it costs nothing. Going back to
a source already searched is allowed only with a new key, once per new value, and the reason is logged:
a name variant (spelling, initials, phonetic forms), adjacent pages of a book that had a hit, the name of
a relative who passes the living-person gate, another collection, another date window, or the next page
of results. This is tabu search with aspiration criteria (`glover1997tabu`) applied to queries, and the
variants come from record-linkage practice (`christen2012datamatching`). A source that returns nothing
three times is closed, following information foraging (`pirolli1999foraging`): leave a patch when it
stops paying. Query rewriting work (`ma2023rewrite`, `wang2023query2doc`, `gao2022hyde`,
`jiang2023flare`) motivates generating new keys instead of re-asking the same question.

**2. Outline first, from several viewpoints.** Before any search, the card (name and birth year) is
turned into an outline of lanes: reference works, military service (only if the person was of age for a
war), census, church, newspapers in three life phases, land, probate and immigration. This follows
STORM and Co-STORM (`shao2024storm`, `jiang2024costorm`), which plan an outline by asking from
different perspectives before writing. Record types that are offline become labelled stubs naming
where to look (for example the FamilySearch Library catalog or a county probate court); nothing is
fetched from FamilySearch.

**3. Parallel workers on Temporal.** Each lane runs as a Temporal child workflow; four run at once
(`temporaldocs`, `temporalpythonsdk`). Anthropic's multi-agent research system found that parallel
subagents with separate context help breadth-first research and that spend explains much of the gain
(`anthropic2025multiagent`); MAST lists the coordination failures to avoid, chief among them duplicated
work (`cemri2025mast`). The shared ledger is that coordination: a worker reserves a call with the parent
before it runs, so two workers can never issue the same call. Tool activities are idempotent, keyed by
the canonical id and reservation, so a retry or a worker crash never runs a finished lookup twice. Long
runs continue-as-new at a round boundary with a compact state.

**4. Best-first lead expansion with a value score.** Within a lane, leads form a tree. The next lead is
picked by a value score (novelty, expected yield, reachability, gap fill, minus cost) plus an
exploration bonus, in the style of UCT (`kocsis2006uct`) and LATS, Tree of Thoughts and RAP
(`zhou2024lats`, `yao2023tot`, `hao2023rap`). There are no simulated rollouts, since each would cost a
real call; instead the reward of a real call is backed up to the lead's ancestors. Across lanes, a UCB1
allocator (`auer2002ucb`) gives more calls to lanes that pay and closes lanes that stay dry, which is
also the spirit of Go-Explore's return to promising states (`ecoffet2021goexplore`).

**5. Reflection between rounds.** After each round, short lessons per lane (for example "this spelling
hits", "this collection is empty for the period") adjust the expected yields and which name variants
are tried next, as in Reflexion (`shinn2023reflexion`). The lessons are rules, not model output, so the
swarm has no model spend.

**6. Verification gate.** A merge step dedupes evidence across workers and admits a hit as a citation
only if the snippet prints the full name, falls inside the person's life window, and does not state a
birth year that contradicts the card. Everything else stays a lead, never a claim. This keeps the
precision guardrail of v0.1, in line with work showing that more agents or more samples help only with
a check on what they return (`wang2023selfconsistency`, `li2024moreagents`, `du2024debate`).

**7. Better tool.** v0.2 adds the Internet Archive full-text search API (`iafts`), which returns
page-level hits and supports result offsets and collection scope. It goes through the same exclusion
filter and tool log, and B1 (ReAct, `yao2023react`) gets it too, so the comparison stays tool-matched.

## How it is measured

Same six people, same frozen answer key v1, same scorer rules, same exclusion filter, B = 100. New: every
run is also re-scored from the first N logged calls (N = the median calls B1 uses, plus a curve at 10,
25, 50, 75 and 100 calls), so a gain from simply spending more calls can be told apart from a gain in
how calls are spent. With six people, and only about four with reachable facts, no difference can be
statistically significant; the preregistered decision rule says what "beats" means instead.

## Post hoc addition: persistent search graph and graph cache

Added after the v0.2 preregistration was committed (and while the preregistered batch was running), at
the owner's request. It is not part of any preregistered condition and is **off for every benchmark
condition**; the batch ran from a commit that does not contain it.

- **Graph export.** Every swarm run writes `<run>.graph.json` (plus `<run>.graphml` and a Mermaid view
  `<run>.mmd`) next to its ledger, built from the ledger by `cr/search_graph.py`. Nodes are entities: the
  person, relatives used as search keys, places named in findings, queries (one per canonical id),
  sources and records. Edges carry provenance: which query searched which source, which query revisited
  which earlier one and why, which query found which record, and which finding (always a "Possible"
  lead, never a claim) that record supports, with a capped snippet as evidence. No page text is stored.
  `scripts/export_graph.py <run dir>` builds the same files for finished runs.
- **Graph cache.** A run started with `ResearchRequest.graph_cache` (a `graph.json` file or a folder of
  them; the harness reads `CR_GRAPH_CACHE`) loads the canonical ids earlier runs executed successfully and
  the ledger skips them with decision `cached`, at no budget cost. Failed calls are not cached, so they can
  be tried again. The harness refuses the cache for benchmark subjects. When the field is unset the
  workflow issues no extra command, so saved histories replay unchanged (`tests/test_replay.py`,
  `tests/histories_swarm/`).
- Tests: `tests/test_search_graph.py` and the end-to-end cache test in `tests/test_swarm_workflow.py`.
